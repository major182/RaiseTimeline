**負荷がかかったときの速さと壊れにくさ**を確かめるテストの決まりごと。正しく動くかは単体・結合・E2E テスト（06）で確かめ、ここでは扱わない。
毎回の CI では動かさず、**必要なときに手で実行する**（機能を大きく変えたとき・デプロイの前など）。

---

## 1. 目的

| 目的 | 確かめること |
|---|---|
| 想定の利用で十分に速いか | 想定ピークで、API の応答時間とエラー率がしきい値（6 章）に収まる |
| どこまで耐えられるか | 利用者を増やしていき、エラー率が上がり始める人数（限界点） |
| 利用者が感じる速さ | 負荷がかかった状態で、ブラウザでの表示・操作がどれだけ遅くなるか |
| 長く動かして壊れないか | メモリの増え続け・DB の接続の枯渇がない |

## 2. 道具

**テストのために本体（画面・API のコード・設定ファイル・ビルドの設定）を変えない。** 性能テストに必要な設定は、すべて `scripts/perf.ts` から起動の引数・環境変数で渡す（例：サーバーの数値の公開、画面の配信）。テストの結果で本体の修正が要ると分かったら、不具合として Issue にする。

| 対象 | 道具 | 選んだ理由 |
|---|---|---|
| API への負荷 | k6 2.3.0（公式の Docker イメージ `grafana/k6:2.3.0`） | シナリオを TypeScript で書け、画面と言語がそろう（k6 は .ts をそのまま実行する）。Docker で動くので PC へのインストールが要らない。しきい値で合否が出る |
| ブラウザでの体感速度 | k6 browser（`grafana/k6:2.3.0-with-browser` に日本語のフォント（Noto CJK）を足したイメージ。`perf/docker/k6-browser.Dockerfile`） | 実際のブラウザで画面を操作し、Web Vitals と手順ごとの所要時間を測る。API の負荷と同じ実行で混ぜられる。書き方が Playwright とほぼ同じで、E2E テストと同じく役割（role）と名前で画面の要素を探せる |
| 画面の表示速度（1 人） | Lighthouse 13.5.0（Node.js から呼ぶ。ブラウザは Playwright 1.64.1 が入れた Chromium） | 本番用のビルドで LCP・CLS・TBT を測る。ログインした後の画面を測るため、Playwright でログインしたブラウザに Lighthouse をつなぐ（Lighthouse CI の自動のログインより簡単で、画面の要素の探し方を E2E とそろえられる） |
| 遅い SQL の特定 | PostgreSQL の `pg_stat_statements`（`db-perf` だけで有効）と `EXPLAIN (ANALYZE, BUFFERS)` | 遅い API の原因を SQL まで追う |

シナリオと実行のスクリプト（`scripts/perf.ts`）は **TypeScript** で書く（画面と同じ言語）。k6 も Node.js 24 も .ts をそのまま実行する。型の定義は `@types/k6`（k6 と同じ版）を使い、
型と整形のチェック（`perf` で `npm run check`）は `node scripts/check.ts` と CI の `perf` ジョブで毎回行う。性能テストそのものは CI では動かさない。

## 3. シナリオ

| ID | 種類 | 負荷 | 目的 | 状態 |
|---|---|---|---|---|
| PT-01 | smoke | 1 人・1 分 | 主な API を一通り呼び、スクリプトと環境が正しいことを確かめる | 実装済み（`perf/k6/scenarios/smoke.ts`） |
| PT-02 | load | 50 人・10 分（2 分かけて増やす） | 想定ピークでしきい値を満たすか | 実装済み（`load.ts`） |
| PT-03 | stress | 50→100→200→300 人（各 3 分） | 限界点。応答時間のしきい値を超えるのは想定のうちで、どの段階で超えたかを読む。失敗が 10% を超えたら途中で止める | 実装済み（`stress.ts`） |
| PT-04 | spike | 10→200 人を 30 秒で、2 分後に 10 人へ | 急に増えたあとに戻るか。合否は失敗の割合（5% 未満）と、戻ったあとの 3 分（`phase:recovery`）の応答時間で見る | 実装済み（`spike.ts`） |
| PT-05 | soak | 30 人・1 時間 | 応答時間が時間とともに悪くならないか。メモリ・DB の接続（HikariCP）が枯れないか（`metrics.jsonl`） | 実装済み（`soak.ts`） |
| PT-06 | web | 1 人。画面ごとに Lighthouse を 3 回（中央値）。パソコンの画面の設定（desktop） | ログイン・タイムライン・プロフィールの表示と、最初に読み込む JS の大きさ | 実装済み（`perf/lighthouse/run.ts`） |
| PT-07 | browser | ブラウザ 1 人で 5 回。ほかの負荷なし | ブラウザでの一連の操作の所要時間（基準の値） | 実装済み（`browser.ts`） |
| PT-08 | hybrid | PT-02 と同じ API の負荷（50 人）＋ ブラウザ 3 人（負荷が 50 人に達してから 10 分） | 負荷がかかった状態で、利用者が感じる速さが PT-07 からどこまで落ちるか | 実装済み（`hybrid.ts`） |

PT-02〜05 の利用者の操作の割合（`perf/k6/lib/behavior.ts`）：タイムライン（全体・フォロー中を半分ずつ）50%、続きの読み込み 15%、プロフィール 10%、いいね 10%、投稿 8%、コメント・返信 5%、利用者の検索 2%。
1 回の操作のあと、画面を読む時間として 1〜3 秒待つ。いいねは今の状態を反対にし（数が増え続けないように）、コメントの半分は既存のコメントへのメンションつきの返信にする。

### 3.1 ブラウザでの操作（PT-07・PT-08）

`perf/k6/lib/browser-flow.ts`。新しいブラウザの画面（Cookie も新しい）で、次の順に操作し、手順ごとに「操作してから結果が画面に出るまで」の時間を記録する。

| 手順 | 操作 | 記録の名前 |
|---|---|---|
| 1 | ログインの画面で入力し、ホームに投稿が出るまで | `step_login` |
| 2 | フォロー中タブに切り替え、投稿が出るまで | `step_tab` |
| 3 | 下までスクロールし、続きが読み込まれるまで（無限スクロール） | `step_load_more` |
| 4 | 投稿を作り、一覧に出るまで | `step_post` |
| 5 | その投稿にいいねし、表示が変わるまで | `step_like` |
| 6 | 投稿の詳細でコメントし、一覧に出るまで | `step_comment` |
| 7 | 返信の欄で `@perf_00` と打ち、メンションの候補が出るまで | `step_mention` |
| 8 | 自分のプロフィールを開き、投稿が出るまで | `step_profile` |

あわせて、k6 が Web Vitals（LCP・INP・CLS・FCP・TTFB）を自動で記録する。
ブラウザの利用者は、API の負荷の利用者とぶつからないよう 901 番以降を使う。
ブラウザは 1 人あたりの CPU・メモリが大きいので、負荷は API の利用者で作り、ブラウザは少数で体感を測る役にする。

## 4. テストデータ

`perf/seed/seed.sql` で、テーブルを作ったあとに一度に入れる。開発用のテストデータ（DB 設計書 7 章）とは分け、Flyway では読み込まない。

| 対象 | 件数 | 作り方 |
|---|---|---|
| 利用者 | 1,000 | パスワードはどれも `pass1234` |
| フォロー | 50,000 | 1 人が次の 50 人をフォロー |
| 投稿 | 100,000 | 直近 30 日に散らす |
| いいね | 500,000 | 1 人 500 件 |
| コメント・返信 | 50,000・10,000 | 返信の本文にはメンションを入れる |

**目印**：利用者のメールは `perf-0001@perf.example.com`、ユーザー名は `perf_0001` の形にする。投稿・いいね・コメント・フォローはすべて目印の利用者にひもづく（テストの途中で作る投稿も含む）ので、目印の利用者から消す対象を決められる。
k6 では、仮想の利用者の番号（VU）ごとに別の利用者でログインする。アクセストークンは 10 分ごとに取り直す（期限は 15 分）。

## 5. テストのあとのデータの削除

| 環境 | 消し方 |
|---|---|
| 手元の DB | 性能テスト用の DB（compose の `db-perf`）を、`perf/seed/cleanup.sql` を流したあと、コンテナと volume ごと消す。開発用の `db`・E2E 用の `db-e2e` には触れない |
| 手元の画像 | 性能テスト用の保存先（`backend/build/perf-media`）を消す |
| 共有の環境（ステージング。予定） | `cleanup.sql` で、目印の利用者にひもづく行だけを 1 万件ずつ消し、`VACUUM ANALYZE` する。条件なしの `DELETE`・`TRUNCATE` は使わない |
| S3 の画像（予定） | 性能テストのときは保存先のキーの先頭を `perf/` にし、その下だけを消す |
| 結果のファイル | `perf/results/` はコミットしない（`.gitignore`） |

- `node scripts/perf.ts` は、**成功・しきい値の不合格・失敗・中断（Ctrl+C）のどれでも、最後に削除する**
- 調べるために残したいときだけ `--keep-data` を付ける。あとから `node scripts/perf.ts cleanup` で消す
- 前回の DB が残っていると、次の実行は始めずに止まる（古いデータで測らないため）
- 削除のあと、目印の利用者・投稿の残りが 0 件であることを `cleanup.sql` が表示する

## 6. 合否のしきい値

初めの値は目安。結果を記録したら見直す。要件の NF-PE-01（タイムラインの 20 件が 1 秒以内）より厳しくし、余裕を見る。

| 対象 | しきい値 | 設定の場所 |
|---|---|---|
| 読み込みの API（タイムライン・一覧など） | p95 < 300ms | `perf/k6/lib/config.ts` |
| 書き込みの API（投稿・いいね・コメント） | p95 < 500ms | 同上 |
| 失敗の割合（4xx・5xx・接続の失敗） | < 1% | 同上 |
| 応答の中身の確認（check） | > 99% | 同上 |

| ブラウザの操作（PT-07・08） | p95 で LCP < 2.5s・INP < 200ms・CLS < 0.1、ログイン→タイムライン < 3s、投稿→一覧に出るまで < 1s | `perf/k6/lib/browser-flow.ts` |

## 7. 実行の方法

先に Docker Desktop を起動しておく。

| 何を | コマンド |
|---|---|
| PT-01 smoke | `node scripts/perf.ts smoke` |
| データを残して実行 | `node scripts/perf.ts smoke --keep-data`（DB は `localhost:5434`） |
| 残したデータを消す | `node scripts/perf.ts cleanup` |
| PT-02〜05 | `node scripts/perf.ts load`（`stress`・`spike`・`soak`） |
| PT-06〜08 | `node scripts/perf.ts web`（`browser`・`hybrid`）。PT-06 は、初めに `cd frontend; npx playwright install chromium` でブラウザを入れておく |
| サーバーの状態を細かく記録 | `node scripts/perf.ts stress --sample-interval=2`（既定は 15 秒ごと。DB の接続の待ちなど短い変化を見るとき） |
| シナリオの動作確認 | `node scripts/perf.ts load --short`（時間を 1/10 に縮める。下の注意を参照） |

`perf.ts` の流れ：

1. 性能テスト用の DB（`db-perf`、ポート 5434）を起動する
2. PT-06〜08 のときは、画面を本番用にビルド（`vite build`）し、API の起動用の出力先（`backend/build/resources/main/static`。Gradle が作る場所で Git の対象外）に写す。本番と同じく、API（Spring Boot）が画面も配信する
3. API を本番に近い設定で起動する（ポート 8092。`dev` を外し、JSON のログ・開発用のテストデータなし。署名の鍵は毎回ランダム。サーバーの数値（metrics）の公開は環境変数で足す）。Flyway がテーブルを作る
4. テストデータを入れる
5. 遅い SQL の集計（`pg_stat_statements`）を空にしてから、k6（Docker）でシナリオを実行する（PT-06 は Lighthouse を Node.js で動かす）。実行中は 15 秒ごとにサーバーの状態を記録する。k6 はしきい値を満たさないと終了コード 99 で終わり、`perf.ts` もその値で終わる
6. 合計の時間が長い SQL の上位 20 件を保存する
7. API を止め、テストデータと写した画面を消す（5 章）

調査・比較用に `--web-server=preview` を付けると、画面を `vite preview`（`perf/web/preview.ts`。ポート 4192）で配信する。`--web-keepalive=秒` で、その配信の使われない接続を閉じるまでの時間を変えられる。どちらも記録には使わない（8 章の PT-08 の調査を参照）

結果は `perf/results/<日時>-<シナリオ>/` に残る。

| ファイル | 内容 |
|---|---|
| `summary.json` | k6 の集計（応答時間の分布・件数・しきい値の合否） |
| `environment.json` | 実行の環境（コミット・OS・CPU・メモリ・k6 の版） |
| `backend.log` | API のログ |
| `web.log` | `--web-server=preview` のときの、画面の配信のログ |
| `k6-raw.json.gz` | PT-07・08 の、1 件ずつの記録（ブラウザの通信の URL・時刻・所要時間など）。遅い通信の原因を調べるときに使う |
| `failure-vu<番号>-iter<回>.png` | ブラウザの操作が途中で止まったときの画面 |
| `lighthouse-summary.json`・`lighthouse-<画面>.json` | PT-06 の画面ごとの中央値と、最後の 1 回の Lighthouse の結果（JSON。Lighthouse Viewer で開ける） |
| `metrics.jsonl` | 15 秒ごとのサーバーの状態（DB の接続の使用中・待ち・上限、ヒープの使用量、スレッド数、CPU）。Actuator の metrics（本体の設定は health だけ。`perf.ts` が環境変数で metrics の公開を足す） |
| `slow-queries.txt` | 合計の時間が長い SQL の上位 20 件（回数・合計・平均・最大・行数） |

**`--short` で分かること・分からないこと**：`--short` は smoke と同じく、**スクリプトが動くか**（API の呼び方・しきい値の判定・記録・削除）を数分で確かめるためのもの。性能の合否・8 章の記録には使わない。

| シナリオ | 縮めると | 性能について言えること |
|---|---|---|
| load | 10 分 → 1 分 | 言えない。件数が少なくばらつきが大きく、JIT（実行中の最適化）が落ち着く前の値が混ざる |
| stress | 各段階 3 分 → 18 秒 | 言えない。DB の接続の待ちなどの詰まりがたまる前に段階が終わる |
| spike | 急増 30 秒 → 3 秒、回復 3 分 → 18 秒 | 言えない。急増は本来より激しく、回復を見る時間が足りない |
| soak | 1 時間 → 6 分 | 言えない。メモリの増え続け・接続の枯渇は時間をかけて現れるため、目的そのものを確かめられない |

**遅い API の調べ方**：しきい値を超えたら、`summary.json` で遅い API（`name` のタグ）→ `metrics.jsonl` で DB の接続の待ち（`dbPending`）やメモリ → `slow-queries.txt` で時間の長い SQL → その SQL を `--keep-data` で残した DB で `EXPLAIN (ANALYZE, BUFFERS)` の順に追う。

**注意**：手元の PC での結果は、PC のほかの処理で揺れる。比べるときは同じ条件で何回か測る。本番の環境には負荷をかけない。

**分かったこと（2026-10-26）**
- 時間の合計の大半は、フォロー中タブの SQL（平均 33ms・最大 168ms）。ほかの SQL は 1ms 未満。利用者が増えたときは、ここが最初に遅くなる
- 300 人で DB の接続（HikariCP の既定の 10 本）を使い切る。さらに増やす前に、接続の数を見直すか、フォロー中タブの SQL を速くする

**分かったこと（2026-10-28）**
- 画面の JS（1 ファイル 672KB）が、API（Spring Boot）から**圧縮されずに**送られている（Lighthouse の通信の記録で、送った大きさ 672KB。gzip なら約 202KB）。本体の設定（`server.compression`）の問題なので、テストでは直さず別の Issue（#90）で扱った

**#90 での修正（2026-10-28）**

2026-10-26・28 に分かった 3 つの課題を、本体の修正として直した。直すたびに性能テストで前後を比べた（上の表の「#90 の修正後」）。

| 課題 | 修正 | 効果 |
|---|---|---|
| 画面の JS が圧縮されない | `server.compression` を有効にした（1KB 以上の JS・CSS・HTML・JSON・SVG） | 送る大きさ 672KB → 210KB、LCP 約 40% 短縮 |
| フォロー中タブの SQL が時間の大半を占める | 実行計画で、いいね経由の側がいいね全件を読み、投稿全件と突き合わせていると分かった。それぞれの側で件数を先に絞り、いいねは集計で求め、投稿者の条件は上位の候補にだけ当てる形に書き換えた。索引 `likes_user_created_idx` に `post_id` を含めた（V10） | 平均 33ms → 10〜12ms。利用者 100 人分の 1・2 ページ目で、修正前と結果が同じことを確かめた |
| 300 人で DB の接続を使い切る | 変えない（SQL が速くなり、接続を使う時間が短くなった） | 300 人で最大 7 本、待ちは 0 回。接続数を増やす根拠がないため、設定はそのまま |

**PT-08 の調査の記録（2026-10-27〜28）**

初めは、画面を `vite preview` で配信して測っていた。このとき、ブラウザの操作の 3〜7% が途中で止まった（通信が 10〜30 秒返らない）。

| 調べたこと | 結果 | 分かったこと |
|---|---|---|
| API のログ | 処理は最長 372ms。止まった要求も、API に届いたあとは 10〜20ms で終わっていた（届くまでに 11〜18 秒） | アプリ（API・DB）は遅れていない |
| ブラウザの通信の記録（`k6-raw.json.gz`） | 遅れは `/api` だけでなく画面のファイル（`/login`）でも起きた。遅れている間も、ほかの通信は 1 秒未満で返っていた | 配信のサーバー全体ではなく、一部の接続だけが詰まる |
| `vite preview` の接続の保持を 5 秒→65 秒（`--web-keepalive=65`） | 3 秒超の通信 14 件→11 件、止まった操作 8 回→5 回（ばらつきの範囲） | 接続の保持の時間は原因ではない |
| 本番と同じく API（Spring Boot）から配信 | 3 秒超の通信 0 件（最大 287ms）、止まった操作 0 回 | **原因はテスト用の配信（`vite preview`）。アプリの不具合ではない** |

これを受けて、画面は本番と同じく API から配信する形を既定にした。あわせて、合否の判定を API とブラウザで分けた（合算していたため、初めの実行ではブラウザの失敗が API の成功に埋もれて合格に見えていた）。
