## 4. 主な設計判断

### 4.1 ログインの方式：JWT（アクセストークン ＋ リフレッシュトークン）

2026-10-09 に、セッション方式から JWT 方式に変更した（利用者の決定）。

| 方式 | 良い点 | 気になる点 | 判定 |
|---|---|---|---|
| **JWT：アクセストークンはメモリ、リフレッシュトークンは HttpOnly Cookie** | 通信のたびに DB を見ずに、どの EC2 でも検証できる。アクセストークンは JavaScript の変数にだけ置くので保存先から盗まれにくく、ヘッダーで送るので CSRF の対象外。リフレッシュトークンは JavaScript から読めない | ログアウトしても、発行済みのアクセストークンは期限（15 分）まで使える。再読み込みでメモリが消えるので、起動時に取り直す仕組みが要る | **採用** |
| JWT：両方 HttpOnly Cookie | 画面の作りが簡単 | Cookie で送るので CSRF の対策が要る | 不採用 |
| JWT：localStorage に保存 | 作りが一番簡単 | XSS があると JavaScript からトークンを盗まれる | 不採用 |
| セッション + Spring Session JDBC | ログアウトですぐ無効にできる | 利用者の決定により JWT に変更（初版で採用していた方式） | 不採用 |

**トークンの決めごと**

| 項目 | アクセストークン | リフレッシュトークン |
|---|---|---|
| 形式 | JWT（HS256 で署名）。中身は利用者の ID（`sub`）・発行者（`iss`）・発行と期限の時刻・トークンの ID（`jti`）だけ。メールアドレスなどは入れない | 推測できないランダムな文字列（256 ビット）。JWT にはしない |
| 期限 | 15 分 | 7 日（取り直すたびに、その時点から 7 日。BR-07） |
| 画面での置き場所 | JavaScript の変数（メモリ）。`localStorage`・`sessionStorage` には置かない | `HttpOnly`・`Secure`・`SameSite=Strict`、`Path=/api/auth` の Cookie（`REFRESH_TOKEN`） |
| 送り方 | `Authorization: Bearer <トークン>` ヘッダー | Cookie（`/api/auth/refresh`・`/api/auth/logout` にだけ送られる） |
| サーバーでの保存 | しない（署名と期限で検証する） | SHA-256 のハッシュだけを DB に保存する（DB 設計書 4.7） |

- **署名の鍵**：256 ビット以上のランダムな値を環境変数 `JWT_SECRET` で渡す。本番の値はパラメータストアに置く（NF-SE-07）。開発用の値だけを `application-dev.yaml` に書く
- **ローテーション**：取り直すたびに新しいリフレッシュトークンを発行し、古いものは無効にする。無効にしたトークンがもう一度使われたら、盗まれたとみなして、その利用者のリフレッシュトークンをすべて無効にする
- **再読み込み**：メモリのアクセストークンは消えるので、画面は起動時に `POST /api/auth/refresh` で取り直す
- **ログアウト**：リフレッシュトークンを DB で無効にし、Cookie を消す。画面はメモリのアクセストークンを捨てる
- **パスワードの変更**：他の端末のリフレッシュトークンをすべて無効にする（今の端末は続けて使える）

### 4.2 画面の配信：Spring Boot から配信する（同じオリジン）

React をビルドした静的ファイルを Spring Boot の `static` に入れ、API と同じ URL から配信する。

- 画面と API が同じオリジンになり、CORS の設定と、Cookie の `SameSite` の悩みがなくなる
- ALB の後ろは EC2 だけで済む（S3 + CloudFront で画面を配信する方法は、構成が増えるため使わない）
- 開発中は Vite の開発サーバーから API へ転送する（`vite.config.ts` の `proxy`）

### 4.3 画像：EC2 を通して S3 に保存し、署名つき URL で見せる

| 方式 | 良い点 | 気になる点 | 判定 |
|---|---|---|---|
| **ブラウザ → EC2 → S3**（サーバーで受けて保存） | 形式・大きさをサーバーで確実に確かめられる（BR-21、BR-22）。作りが単純 | EC2 を画像が通る（5MB × 4 枚なら問題ない） | **採用** |
| ブラウザ → S3 に直接（署名つき URL でアップロード） | EC2 の負荷が減る | 中身の確認を後から行う仕組みが要る | 不採用 |

- 表示は、S3 の**署名つき URL**（期限 1 時間程度）を API の応答に含めて返す（NF-PE-03、NF-SE-06）
- 開発環境では、S3 の代わりにローカルのフォルダに保存する（保存先を差し替えられる作りにする）

### 4.4 タイムラインの読み込み

どの一覧も**カーソル方式**で続きを読む（BR-53）。「何ページ目」で取る方式（OFFSET）ではなく、「最後に表示したものより後に並ぶもの」を取るので、読んでいる間に新しい投稿が増えても重複せず、件数が増えても遅くなりにくい。

| 一覧 | 並びの基準（新しい順） | カーソル |
|---|---|---|
| 全体タブ・利用者ごと | 投稿日時 | 最後に表示した投稿の (投稿日時, ID) |
| フォロー中タブ | 並びの時刻（下の表） | 最後に表示した項目の (並びの時刻, 投稿の ID) と、基準の時刻 |

**フォロー中タブの「並びの時刻」**

| 投稿の種類 | 並びの時刻 |
|---|---|
| 自分・フォロー中の人の投稿 | 投稿日時 |
| いいね経由の投稿（BR-50-3） | フォロー中の人がその投稿にいいねした時刻のうち、**基準の時刻より前で最も新しいもの** |

- 基準の時刻は、最初に読み込んだ時刻。読み進めている間についた新しいいいねで投稿が上に移動し、重複・欠落が起きるのを防ぐ
- フォロー中の人の投稿に、フォロー中の人がいいねしていても、フォロー中の投稿として1回だけ出す
- 2つの種類を UNION でまとめ、(並びの時刻, 投稿の ID) の降順で 20 件取る

**留守中のハイライト**（BR-52）

- 利用者に「最後にタイムラインを開いた時刻」を持たせ、フォロー中タブの最初の読み込みのときに更新する
- 前回から 6 時間以上あいていれば、その間のフォロー中の投稿（自分を除く）から「いいねの数 + コメントの数 × 2」の多い順に最大 3 件を選ぶ
- 選んだ投稿の ID を、その下の一覧から除く

**索引**（NF-PE-01）：投稿の (投稿日時, ID)、(投稿者, 投稿日時)、いいねの (投稿, 利用者)・(利用者, 日時)、フォローの (フォローする人, フォローされる人)

### 4.7 XSS の対策（NF-SE-05）

XSS（他人が書いたスクリプトを画面で動かされる攻撃）があると、メモリのアクセストークンも盗まれうる。トークンの置き場所だけに頼らず、次を重ねる。

| No | 対策 | 内容 |
|---|---|---|
| S-01 | エスケープ | 投稿・コメントなど利用者が書いた文字は、React の通常の表示（`{text}`）だけで出す。React が自動でエスケープするので、HTML として動かない |
| S-02 | 危険な書き方の禁止 | `dangerouslySetInnerHTML`・`eval`・`new Function` などを ESLint で禁止する（CI で検出する） |
| S-03 | Content-Security-Policy | Spring Boot が返すすべての応答に付ける。`script-src 'self'` で自分のサイトのスクリプトだけを動かし、外部やインラインのスクリプトを止める。Material UI がスタイルを差し込むため `style-src` は `'unsafe-inline'` を許す |
| S-04 | トークンを保存しない | アクセストークンはメモリだけ、リフレッシュトークンは `HttpOnly` の Cookie。XSS があっても、保存先からまとめて盗まれない |
| S-05 | 外部のスクリプトを読み込まない | 画面のファイルはすべて自分で配信し、CDN などから読み込まない |
| S-06 | 移動先の制限 | ログインの後に戻る先は、アプリの中の URL（`/` で始まり `//` で始まらない）だけにする |
| S-07 | そのほかのヘッダー | `X-Content-Type-Options: nosniff`、`X-Frame-Options: DENY`（`frame-ancestors 'none'`）、`Referrer-Policy: strict-origin-when-cross-origin` |

- 開発中は画面を Vite が配信するため、CSP は付かない（Vite の画面の自動更新がインラインのスクリプトを使うため）。CSP の確認は、Spring Boot から画面を配信する本番の形で行う
